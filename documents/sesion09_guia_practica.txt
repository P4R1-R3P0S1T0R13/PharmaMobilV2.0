Abre AppModule.kt y los dos archivos PlatformModule: el mecanismo expect/actual ya existe en el proyecto

4. Marco conceptual de apoyo 
Kotlin Multiplatform no promete compartirlo todo: promete compartir lo que tiene sentido compartir. El 
modelo de dominio, los casos de uso, el consumo REST y la interfaz Compose viven una sola vez en 
commonMain. Lo que depende del sistema operativo —formatos locales, permisos, sensores, compartir, 
almacenamiento seguro— necesita una implementación por plataforma. 
El mecanismo expect/actual permite declarar en el código común qué debe existir, sin decir cómo se resuelve. 
Cada source set de plataforma aporta su actual, y el compilador exige que estén todos: si falta uno, el proyecto 
no compila. Ese es el valor del mecanismo frente a comprobaciones en tiempo de ejecución. 
 
Concepto Definición operativa 
expect Declaración sin cuerpo en commonMain. Dice qué debe existir. 
actual Implementación en un source set de plataforma. Debe coincidir en nombre, 
paquete y firma. 
Biblioteca de plataforma Kotlin/Native expone UIKit y Foundation como paquetes normales: 
platform.UIKit.UIDevice se importa como cualquier clase. 
Framework compartido El módulo shared se compila como un framework que Xcode importa con import 
Shared. 
Sufijo Kt Kotlin agrupa las funciones de nivel superior de un archivo en una clase con ese 
sufijo: MainViewControllerKt. 
Prefijo do Swift reserva los nombres que empiezan con init para los constructores, así que 
initKoinIos() se invoca como doInitKoinIos().

La combinación de esta práctica 
El formateo de moneda se resuelve con expect/actual, porque es una función pura sin dependencias. Compartir 
se resuelve con una interfaz en domain y una implementación por plataforma, registradas dentro del expect val 
platformModule que el proyecto ya tien e. Así el compilador sigue exigiendo ambas implementaciones y las 
pruebas pueden sustituirlas. 
5. Desarrollo de la práctica 
Ejecuta los seis pasos en orden. No avances al siguiente hasta que el anterior compile en ambas plataformas. 
Paso 1. Declarar la primera capacidad: formato de moneda 
PharmaSoft envía el precio como número; mostrarlo correctamente es responsabilidad de cada plataforma. 
Crea el archivo en commonMain y deja que el compilador te reclame los actual. 
// commonMain/platform/Formato.kt 
package pe.edu.upeu.pharmamobil.platform 
  
expect fun formatearSoles(valor: Double): String 
 
Punto de control 1 
Compila el proyecto. Debe fallar con un mensaje que indica que faltan las declaraciones actual para androidMain 
e iosMain. Ese error es la prueba de que el mecanismo funciona: lee el mensaje antes de continuar.  
Paso 2. Escribir los dos actual 
Ambos archivos deben declarar el mismo paquete y la misma firma que el expect. 
// androidMain/platform/Formato.android.kt 
package pe.edu.upeu.pharmamobil.platform 
  
import java.text.NumberFormat 
import java.util.Locale 
  
actual fun formatearSoles(valor: Double): String = 
    NumberFormat.getCurrencyInstance(Locale("es", "PE")).format(valor)

// iosMain/platform/Formato.ios.kt 
package pe.edu.upeu.pharmamobil.platform 
  
import platform.Foundation.* 
  
actual fun formatearSoles(valor: Double): String { 
    val formateador = NSNumberFormatter() 
    formateador.numberStyle = NSNumberFormatterCurrencyStyle 
    formateador.locale = NSLocale("es_PE") 
    return formateador.stringFromNumber(NSNumber(valor)) 
        ?: "S/ $valor" 
} 
 
Aplica el formato donde corresponde: en el mapeo a ProductoUi de la capa de presentación, no dentro del 
composable ni en el modelo de dominio. 
// presentation/producto/ProductoUi.kt 
fun Producto.toUi() = ProductoUi( 
    id = id, 
    nombre = nombre, 
    precio = formatearSoles(precio), 
    stock = stock 
) 
 
Punto de control 2 
El proyecto compila y el listado muestra el precio formateado. Compara el resultado en los dos dispositivos: los 
separadores y la posición del símbolo pueden diferir, y esa diferencia es precisamente lo que no podías resolver 
en código común. 
Paso 3. Declarar la segunda capacidad como contrato del dominio

Por eso aquí conviene una interfaz, no un expect. 
// commonMain/domain/platform/Compartidor.kt 
package pe.edu.upeu.pharmamobil.domain.platform 
  
interface Compartidor { 
    fun compartir(texto: String) 
}

Paso 4. Implementar la capacidad en cada plataforma 
// androidMain/platform/CompartidorAndroid.kt 
class CompartidorAndroid( 
    private val contexto: Context 
) : Compartidor { 
  
    override fun compartir(texto: String) { 
        val envio = Intent(Intent.ACTION_SEND).apply { 
            type = "text/plain" 
            putExtra(Intent.EXTRA_TEXT, texto) 
        } 
        val selector = Intent.createChooser(envio, null).apply { 
            addFlags(Intent.FLAG_ACTIVITY_NEW_TASK) 
        } 
        contexto.startActivity(selector) 
    } 
}

// iosMain/platform/CompartidorIos.kt 
class CompartidorIos : Compartidor { 
  
    override fun compartir(texto: String) { 
        val controlador = UIActivityViewController( 
            activityItems = listOf(texto), 
            applicationActivities = null 
        ) 
        UIApplication.sharedApplication 
            .keyWindow 
            ?.rootViewController 
            ?.presentViewController(controlador, true, null) 
    } 
} 
 
Por qué FLAG_ACTIVITY_NEW_TASK 
El Context que Koin entrega es el de la aplicación, no el de una Activity. Lanzar una Activity desde el contexto 
de aplicación exige esa bandera; sin ella, Android lanza una excepción en tiempo de ejecución.  
Paso 5. Llenar el platformModule de cada plataforma 
Los dos módulos del proyecto están vacíos desde la Unidad 1. Este es el momento para el que fueron creados. 
// androidMain/di/PlatformModule.android.kt 
actual val platformModule: Module = module { 
    single<Compartidor> { CompartidorAndroid(androidContext()) } 
} 
  
// iosMain/di/PlatformModule.ios.kt 
actual val platformModule: Module = module { 
    single<Compartidor> { CompartidorIos() } 
}

6. Interoperabilidad Kotlin-Swift en tu propio proyecto 
PharmaMobil ya contiene dos archivos Swift que usan tu código Kotlin desde la Unidad 1. Ábrelos y obsérvalos 
con lo aprendido hoy. 
 
Lo que ves en Swift Por qué se llama así 
KoinIosKt.doInitKoinIos() Kotlin agrupa las funciones de nivel superior del archivo KoinIos.kt 
en la clase KoinIosKt. El prefijo do aparece porque Swift reserva 
los nombres que empiezan con init para los constructores. 
MainViewControllerKt.MainViewController() Mismo criterio: la función de nivel superior de 
MainViewController.kt queda dentro de una clase con sufijo Kt. 
import Shared El módulo shared se compila como framework; Shared es el 
nombre con el que Xcode lo importa. 
 
6.1 Lo que cambia al cruzar 
• Las funciones suspend se exponen como funciones async de Swift; para poder capturar errores deben 
anotarse con @Throws en Kotlin. 
• Las sealed classes llegan como jerarquías de clases y pierden la exhaustividad: el switch de Swift siempre 
pedirá un default. 
• Las data classes pierden copy y la desestructuración; se usan como clases normales. 
• Los tipos anulables de Kotlin llegan como opcionales de Swift; los no anulables, como valores directos. 
 
Consecuencia de diseño 
Como la exhaustividad del when no cruza a Swift, la lógica de estados debe quedarse en Kotlin. Si alguien del 
equipo integra una pantalla SwiftUI, debe consumir un estado ya resuelto, no reconstruir la decisión en el otro 
lado.
